# Engineering controls of the Go bindings (AF-CTR-01)

AF-CTR-01 adds the Go module `github.com/ArcForges/Contracts/go` (directory `go/`) beside the C# and
npm outputs ([architecture](architecture.md#go-bindings-af-ctr-01)). This page maps every existing
control of the repository to its Go equivalent, or records why none applies, with the entry point
that runs it and the stage where it runs. The stages are the steps of the Linux leg in
`eng/verify_steps.py` (the host verification after the push, [AGENTS.md](../AGENTS.md#verification-after-the-push-ad-0020))
and the hosted jobs of `.github/workflows/ci.yml` and `security.yml` (external PRs, main and tag
pushes, the weekly schedule).

Practices of the surveyed Go projects that are not adopted here: golangci-lint (its relevant
analysers are `go vet` and staticcheck, which run with every check enabled, and the module has no
handwritten production code), fuzzing (the bindings contain no handwritten parser; fuzz targets
belong to the center's own parsers, AF-CTR-02), macOS and 32-bit matrices (outside the platform
scope) and harden-runner.

## Generated packages beyond the task's list

The AF-CTR-01 task names `foundation.v1`, `hello.v1`, `publicapi.v1`, `node.v1`, `fleet.v1` and
`relay.v1`. The module also generates two more packages:

- **`operator.v1` (internal).** It holds `OperatorService` and `OperatorReadService`. The Go center
  replaces the C# center host (AD-0021 §15) and takes over the retained business capabilities (§14),
  so it serves the operator contracts.
- **`catalog.v1` (public).** It is generated only because
  `internal/proto/arcforges/operator/v1/operator.proto` imports `arcforges/catalog/v1/catalog.proto`.
  No other package of the module imports it, and a Go package needs its whole import closure in the
  module.

## Fixture coverage

The Go tests (`go/internal/compat`) read exactly these fixtures under `fixtures/public`:

| Fixture                          | What the Go tests check                                                                                                                                                      |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `wp03-01.json`                   | the 10 wire oracles byte for byte, and its positive foundation cases                                                                                                         |
| `con-02-descriptors.json`        | the descriptor wire vectors, and the positive cases of its exchange section                                                                                                  |
| `con-09-sync-transfer.json`      | the positive `TransferTicket` cases                                                                                                                                          |
| `wp03-02.json`                   | the serialization vectors under the WP03.02 byte and depth limits                                                                                                            |
| `con-03-sync-allowlist.json`     | the forward-compatible `AggregateBody` response with its unknown member, and the opaque body cases                                                                           |
| `hello.json`                     | the Hello cases over Connect, gRPC and gRPC-Web (binary codec only)                                                                                                          |
| `af-con-01-error-catalogue.json` | every catalogued code, with each of its retry modes and effects, as an `ArcError` Connect error detail over Connect, gRPC and gRPC-Web, cycling through all 16 Connect codes |

The positive cases of the first three files are the 234 foundation fixture cases. In Go each one
encodes, decodes to the same value and re-encodes to the same bytes, and the exchange also reads
their C# encodings. Every other message of the module is covered by the exchange's synthesized
samples (one per message and oneof arm), not by an authored fixture.

The protobuf-JSON value fixtures of the other contract areas are read only by the C# suites and the
tooling tests, not by Go. Examples are `con-07-identity.json`, `con-08-entitlement-commerce.json`,
`fixtures/internal/con-14-operator.json` and `con-22-account-support.json`.

## Vulnerability check and delivery

govulncheck reads a vulnerability database that changes independently of the commit. Main and `v*`
pushes run delivery only ([AGENTS.md](../AGENTS.md)), so `ci.yml` runs `go check --no-vulncheck`
there, and a newly disclosed advisory never blocks the NuGet, npm and Go publication of a commit that
was already verified. govulncheck still runs:

- in the host verification (`go-vulncheck`);
- in the Go checks of external PRs, the merge queue and manual CI runs;
- in the weekly and manually dispatched `Go vulnerability check` job of `security.yml`.

A finding is fixed by a reviewed dependency update.

## Byte order of Go and C# encodings

The exchange proves equal meaning in both directions, not equal bytes. protobuf-go writes the
members of a (non-synthetic) `oneof` after the other fields of a message, "to preserve compatibility
with historic wire output", while the C# runtime writes every field in field-number order. Both are
valid protobuf encodings and each runtime reads the other's bytes to the same value; at AF-CTR-01,
2,300 of the 2,391 exchange samples and 189 of the 234 foundation fixture cases are byte-identical,
and every difference is this field order. A consumer must therefore never compare, hash or sign a
re-encoding produced by another runtime: digests and signatures (for example the payload digest of
idempotent commands and the signed routed calls of AD-0021 §10) are computed over the bytes as sent.

## Windows leg assessment

Contracts has one verification leg, on Linux, and its `main` ruleset requires only
`arcforges/linux`. The Go bindings add no behaviour that needs a Windows leg:

- **Generation is platform-independent and checked byte for byte.** The generators are pure Go
  programs built from `go.sum`-verified sources with the pinned Go release, and `protoc` is the same
  Grpc.Tools release on both platforms. Proto file names reach the plugins as `/`-separated virtual
  paths (`-I` include roots), the M options use those paths, the plugins write LF output, and the
  generated packages are committed. The Linux drift step fixes the bytes every consumer receives.
- **Checkouts keep LF.** `.gitattributes` (`* text=auto eol=lf`) checks the generated files out with
  LF on Windows, and `gofmt` accepts them unchanged.
- **The module is source.** Consumers compile it with their own toolchain on their own legs: the Go
  center (AF-CTR-02) builds and tests on both native legs of the Cloud repository (AD-0021 §16), which
  exercises these packages on Windows where it matters.
- **The race detector is Linux-only** in this setup (no cgo on the Windows host); Go tests on Windows
  would run without it, so a Windows leg would add no data-race coverage.

To support this assessment, the Go generation check and the build and tests of the module are also run on
the Windows host at the AF-CTR-01 head; the pull request records the result. A Windows leg would re-prove
only platform-independent generation; it is not added, and no ruleset change is needed.
